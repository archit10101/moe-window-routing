# MoE window-routing pilot: runbook

Every command in order, from the laptop tests to the final analysis. The spec is in `docs/PROMPT.md`.

Two arms, identical except for the router input in layers 5–8:

- **baseline** routes on each token's own hidden state.
- **win16** routes on the causal mean of the last 16 hidden states.

Runs are defined in `config/runs/`, which is generated by `scripts/make_configs.py`. Every default lives in `config/pilot_base.py`.

## 2. MIT Engaging (Slurm), the primary route

All paths below assume `PROJECT=/home/architta/orcd/scratch/moe-pilot`. The data is already in `$PROJECT/data/`.

### 2.1 Clone and activate (once)

```bash
ssh <you>@<engaging-login-host>                      # your usual Engaging login node
export PROJECT=/home/architta/orcd/scratch/moe-pilot
cd $PROJECT
git clone https://github.com/archit10101/moe-window-routing.git code
cd $PROJECT/code

module load miniforge
source "$(conda info --base)/etc/profile.d/conda.sh"
conda activate moe
python -c "import torch, numpy; print(torch.__version__, torch.version.cuda)"
python -c "import matplotlib" || pip install matplotlib   # only analysis/analyze.py needs it

ls -la $PROJECT/data && head -c 400 $PROJECT/data/meta.json   # train.bin, val_*.bin, meta.json
python -m pytest -q                                # optional: the CPU tests also pass here
```

Run every later command from `$PROJECT/code` with the `moe` env active. The scripts write run folders to `$PROJECT/runs/<run>/`, and Slurm logs go to `$PROJECT/runs/slurm/`.

### 2.2 GPU smoke test (2 × 200 steps, 30 minutes)

```bash
scripts/slurm/submit_smoke.sh b200
scripts/slurm/status.sh                            # repeat until both rows say done = yes
tail -n 30 $PROJECT/runs/smoke-gpu-base/stdout.log
```

Check the following:

- Both runs reach step 200 and write `done`.
- Train CE falls from about 10.8 (ln 50304) to well below 8.
- `val_overall` is logged at steps 0, 100 and 200.
- No NaNs.
- `load_max`/`load_min` in `log.jsonl` stay roughly between 0.02 and 0.5.

### 2.3 Benchmark and memory check (decides 4 runs per B200)

```bash
scripts/slurm/benchmark.sh b200
# when the job finishes:
grep -h "BENCHMARK\|case\|copy" $PROJECT/runs/slurm/benchmark-*.out
```

Each line reports `tok_per_s` and `peak_mem_gb` for one process. Read them like this:

- **Memory:** 4 × the per-copy `peak_mem_gb` must fit comfortably on the GPU (B200 ≈ 180 GB, so aim for ≤ ~160 GB in total). If any copy failed with "CUDA out of memory", or the total is too close, switch to micro-batch 16:

  ```bash
  sed -i 's/^micro_batch_size = 64$/micro_batch_size = 16/' config/pilot_base.py
  grep micro_batch_size config/pilot_base.py         # should print 16
  scripts/slurm/benchmark.sh b200                     # re-check
  ```

  The effective batch stays 64 × 1024 tokens (grad_accum = 4), so the results are unaffected. Change it **before** the LR check, so that every run uses the same value.
- **Throughput:** 4-copy efficiency = (sum of the 4 copies' tok/s) / (single tok/s). If it's ≥ ~1.2, sharing the GPU is worthwhile.
- **Time:** per-run hours ≈ 500e6 / (per-copy tok/s) / 3600. One job runs 5.5 h and requeues itself up to 3 times (4 × 5.5 h ≈ 22 h in total). If a run needs more than that, resubmit the same group by hand; it resumes from its checkpoint.

### 2.4 LR check (6 runs × 100M tokens)

```bash
scripts/slurm/submit_lr_check.sh b200              # 2 jobs of 3 runs (l40s: 6 single-run jobs)
scripts/slurm/status.sh                            # wait until all six lr-* rows say done = yes
```

### 2.5 Choose the LRs

```bash
python analysis/analyze.py --runs_dir $PROJECT/runs --out_dir $PROJECT/analysis/lr_check --lr_check --write
cat config/chosen_lr.py                            # LR_BASE and LR_WIN are now numbers
```

The rule: take the lowest final `val_overall`. If another LR is within 0.01 of it, take the lowest such LR. The main runs read `config/chosen_lr.py` when they start, so it must be set in `$PROJECT/code` before you submit. To keep a record, commit it (`git add config/chosen_lr.py && git commit -m "Chosen LRs"`) and push from the cluster, or copy the two numbers into the repo on your laptop.

### 2.6 Main runs (8 runs × 500M tokens)

```bash
scripts/slurm/submit_main.sh b200                  # job A: base-s0 win16-s0 base-s1 win16-s1
                                                   # job B: base-s2 win16-s2 win1-s0 win64-s0
```

`submit.sh` refuses to submit while `chosen_lr.py` still has `None`. The per-user limit is 2 GPUs, so submit main runs only after the LR-check jobs have finished.

### 2.7 Monitor

```bash
scripts/slurm/status.sh                            # step, tokens, train CE, tok/s, val_overall, done + squeue
tail -f $PROJECT/runs/base-s0/stdout.log
ls $PROJECT/runs/slurm/                            # <job-name>-<jobid>.out and requeue_<jobid>.count
```

Jobs requeue themselves until every run in the group is done, with at most 3 requeues per job. If a group is still unfinished after that, resubmit it: `scripts/slurm/submit.sh main-A b200 05:30:00 base-s0 win16-s0 base-s1 win16-s1` (runs that are already done are skipped).

### 2.8 Optional extra seeds (after the main runs; uses 1 GPU)

```bash
scripts/slurm/submit_extra_seeds.sh b200           # base-s3 win16-s3 base-s4 win16-s4
```

### 2.9 Analysis

```bash
python analysis/analyze.py --runs_dir $PROJECT/runs --out_dir $PROJECT/analysis/main
cat $PROJECT/analysis/main/summary.md              # verdict, gap, s and every final value
# copy everything to the laptop:
scp -r <you>@<engaging-login-host>:$PROJECT/analysis/main ./analysis_main
```

The analysis uses every finished seed and needs at least 2 per arm, plus `win1-s0` and `win64-s0`. It exits with code 2 and writes "No verdict yet" until those runs exist. Outputs:

- `sanity.png`, `main_comparison.png`
- `per_source.{csv,md}`
- `window_sweep.png`, `loads.png`
- `routing_heatmap.png`, `routing_mi.csv`
- `summary.md`

### 2.10 Plan B: L40S (48 GB)

Use `l40s` in place of `b200` in every command. The convenience scripts then submit one run per job; two run at a time and the rest queue. Before the LR check, set `micro_batch_size = 16` (section 2.3), because 64 is likely too large for 48 GB. Check it with `scripts/slurm/benchmark.sh l40s`, which tells you the single-copy memory (ignore the 4-copy case on L40S). The smoke job still runs both smoke runs on one GPU, so use micro-batch 16 for it too.

## 3. AWS fallback (us-east-2, g6e instances)

### 3.1 Bucket and data (once, from any machine with AWS credentials and the data)

```bash
export S3_BUCKET=<choose-a-name>                   # every AWS script reads this
aws s3 mb s3://$S3_BUCKET --region us-east-2
aws s3 sync /home/architta/orcd/scratch/moe-pilot/data/ s3://$S3_BUCKET/data/   # train.bin, val_*.bin, meta.json
```

### 3.2 Each instance

Launch a g6e.12xlarge (4 × L40S) or g6e.xlarge (1 × L40S) with the Deep Learning AMI with PyTorch and the S3 IAM role. Its shutdown behavior is set to terminate. Then:

```bash
ssh ubuntu@<instance>
git clone https://github.com/archit10101/moe-window-routing.git /home/ubuntu/code
export S3_BUCKET=<bucket>
bash /home/ubuntu/code/scripts/aws/setup_instance.sh   # env, pip deps, git pull, data sync, nvidia-smi
cd /home/ubuntu/code
```

L40S has 48 GB, so set micro-batch 16 first and check memory:

```bash
sed -i 's/^micro_batch_size = 64$/micro_batch_size = 16/' config/pilot_base.py
source scripts/aws/env.sh && activate_pytorch
CUDA_VISIBLE_DEVICES=0 python train.py config/runs/smoke-gpu-base.py --benchmark_steps=30 \
    --data_dir=/home/ubuntu/data --out_root=/home/ubuntu/runs | grep BENCHMARK
```

### 3.3 Smoke, LR check, main runs

`launch_instance.sh` runs one run per GPU (GPUs 0..k−1) and shuts the instance down once every listed run is `done`. Add `--no-shutdown` as the first argument to keep the instance up.

```bash
# smoke (any instance; --no-shutdown so you can continue on it)
bash scripts/aws/launch_instance.sh --no-shutdown smoke-gpu-base smoke-gpu-win16

# LR check: 6 runs, e.g. two 4-GPU instances
bash scripts/aws/launch_instance.sh lr-base-1e-3 lr-base-2e-3 lr-base-4e-3        # instance 1
bash scripts/aws/launch_instance.sh lr-win16-1e-3 lr-win16-2e-3 lr-win16-4e-3     # instance 2

# choose LRs (on any machine with the repo and S3 access)
aws s3 sync s3://$S3_BUCKET/runs/ ./runs_s3/ --exclude "*/ckpt/*"
python analysis/analyze.py --runs_dir ./runs_s3 --out_dir ./analysis_lr --lr_check --write
git add config/chosen_lr.py && git commit -m "Chosen LRs" && git push    # then `git pull` on each instance

# main runs: two 4-GPU instances
bash scripts/aws/launch_instance.sh base-s0 win16-s0 base-s1 win16-s1   # instance A
bash scripts/aws/launch_instance.sh base-s2 win16-s2 win1-s0 win64-s0   # instance B
```

### 3.4 Monitor and analyze

```bash
tail -f /home/ubuntu/launch_logs/base-s0.log       # retries, sync, shutdown messages
tail -f /home/ubuntu/runs/base-s0/stdout.log
python scripts/status.py /home/ubuntu/runs
aws s3 ls s3://$S3_BUCKET/runs/                    # synced every 5 min (ckpt every 15 min)

# when everything is done
aws s3 sync s3://$S3_BUCKET/runs/ ./runs_s3/ --exclude "*/ckpt/*"
python analysis/analyze.py --runs_dir ./runs_s3 --out_dir ./analysis_main
```

If an instance dies, start a new one and run `launch_instance.sh` with the same runs. `launch_run.sh` pulls the run folder (including the checkpoint) from S3 and resumes it.

## 4. Troubleshooting

- **"LR_BASE in config/chosen_lr.py is still None":** finish the LR check and run `analyze.py --lr_check --write` (section 2.5).
- **A run won't start and its stdout.log says "nothing to do":** it already has `done`. To rerun it, delete or rename `$PROJECT/runs/<run>`.
- **"checkpoint ... was made with a different config":** you changed a hyperparameter in the middle of a run. Revert the change, or delete the run folder to start over. Changing `micro_batch_size` mid-run is allowed, with a warning.
- **CUDA out of memory:** set `micro_batch_size = 16` in `config/pilot_base.py` (section 2.3). It's the only place it is set.
- **Exit code 99 in stdout.log:** normal. The run was signaled near the time limit, saved a checkpoint and will resume on requeue or resubmit.
- **"requeue limit (3) reached":** resubmit the group with `scripts/slurm/submit.sh` (section 2.7).
- **Job pending a long time:** `squeue -u $USER -o "%.10i %.20j %.8T %.20R"` shows the reason. The limit is 2 GPUs per user at once.
- **Slurm can't find the code:** jobs use `$PROJECT/code`. Override with `CODE_DIR=... scripts/slurm/submit.sh ...` if you cloned elsewhere.
- **train.py says "run this from the repository root":** `cd` into the code directory first.
- **AWS script says S3_BUCKET is not set:** `export S3_BUCKET=<bucket>` in that shell (and before `launch_instance.sh`).
- **setup_instance.sh can't find the PyTorch environment:** follow its message (look in `/opt` or the AMI README), activate the environment by hand, then rerun.
